# 中国区部署与合规设计草案

> **适用对象**：在中国境内提供服务的 B2B SaaS
> **文档性质**：技术侧落地路径梳理，**不构成法律意见**。带 ⚠️ 的条目需法务或合规顾问确认。
> **状态**：草案 v0.1

本文回答一个问题：**SaaS 要在中国境内合规地跑起来，技术侧需要提前做什么。**

---

## 0. 为什么需要这份文档

中国区的合规不是上线前的"最后一道手续"，而是会影响架构选型的**前置约束**。典型的连锁反应：

```
等保定级  → 决定是否需要密码评估（密评）  → 决定是否必须用国密算法
                                          → 决定密钥管理体系（KMS/HSM）
等保定级  → 决定审计日志的范围与保留期
数据分类分级 → 决定图纸能否出境 → 决定日本总部能否直连中国区数据
```

**结论：定级和数据分类要在写第一行生产代码之前完成。** 事后改造的成本远高于事前设计。

## 2. 合规要求逐项拆解

### 2.1 网络安全等级保护 2.0（等保）

**依据**：《网络安全法》+ GB/T 22239-2019《信息安全技术 网络安全等级保护基本要求》

**先做的事：定级。** 定级由两个要素决定——受侵害的**客体**（公民法人权益／社会秩序公共利益／国家安全）和**侵害程度**。

| 定级 | 典型判断 | 对本项目 |
|---|---|---|
| **2 级** | 一般企业系统；受侵害严重损害法人合法权益，或损害社会秩序公共利益 | 若客户为普通制造业企业、图纸不含敏感数据 |
| **3 级** | 受侵害严重损害社会秩序公共利益，或损害国家安全 | 若客户含关键信息基础设施运营者、涉及重要数据、或平台汇集大量客户图纸 ⚠️ |

**关键判断点（必须与法务确认）**：

- ⚠️ 平台是**多租户 SaaS**，汇集多家制造业客户的图纸。即使单个客户的图纸不敏感，**汇集的整体**是否构成"重要数据"？
- ⚠️ 若客户群中出现 CII（关键信息基础设施）运营者，作为其服务提供方，等保等级通常需对齐

**2 级与 3 级的工程差异**（这是真正影响成本的部分）：

| 控制项 | 2 级 | 3 级 |
|---|---|---|
| 安全通信网络／区域边界 | 基本要求 | **更严**，需边界入侵防范、恶意代码防范 |
| 安全计算环境 | 身份鉴别、访问控制、审计 | **＋ 入侵防范、可信验证、数据完整性** |
| **安全管理中心** | 不强制 | **强制**（集中管控：日志、安全态势） |
| **密评** | 一般不强制 | **强制**（见 2.2） |
| 测评频率 | 备案 + 定期测评 | 备案 + **每年至少一次**测评 |

**行政流程**：向**公安机关**备案 → 由有资质的测评机构测评 → 出具备案证明与测评报告。

**Demo 的差距**（等保第一个会指出的问题）：**无身份鉴别、无访问控制、无审计日志**。这三项是"安全计算环境"的最基础要求。

### 2.2 商用密码（SM2／SM3／SM4）

**依据**：《密码法》（2020-01-01 施行）+ 《商用密码应用安全性评估管理办法》

**是否需要做密评**：

- 关键信息基础设施 → **必须**
- 等保 **3 级及以上** → **必须**
- 等保 2 级、政务系统 → 视具体要求 ⚠️

**算法用途映射**：

| 算法 | 类型 | 在本系统中的用途 |
|---|---|---|
| **SM4** | 对称加密 | 图纸文件、元数据、个人信息的**存储加密**；数据库字段级加密 |
| **SM2** | 非对称／签名 | **电子签名**（审查确认、批准记录）、密钥交换 |
| **SM3** | 哈希 | **完整性校验**（图纸不可篡改证明）、审计日志防篡改链 |

**当前差距**：Laravel 默认使用 AES-256-CBC + HMAC-SHA256。这在密码学强度上没有问题，但**不满足国密要求**。

**改造路径与成本提示**（这部分要在立项时讲清楚）：

1. 引入支持国密的密码库（如 GmSSL，或云厂商的 KMS 国密版）
2. 数据存储层：字段级加密改为 SM4，历史数据需**迁移重加密**
3. 签名与审计：SM2 签名 + SM3 哈希链
4. **密钥管理是本项最难的部分**：密钥不能放在配置文件里，需 KMS 或 HSM，并配套轮换与权限分离
5. ⚠️ 历史数据迁移与"迁移期间双算法并存"的方案需专门设计

> **表达要点**：这一项不是"换个库"就能解决的，**密钥管理体系的建设周期通常比算法替换长得多**。

### 2.3 个人信息保护法（PIPL）

**依据**：《个人信息保护法》（2021-11-01 施行）

**制造业图纸里为什么会有个人信息**：

- 设计图／检验记录／受入记录中的**签字人、审批人、工号**
- 系统操作日志中的用户行为

**本 Demo 的情况（重要）**：演示数据**刻意不含任何个人信息**——`inspection_report.json` 中的 `記録者` 只是「公開デモ検査担当」这样的职务名占位，全仓库不存在真实姓名。但**生产系统一定会引入**这些字段：客户的图纸和检验记录上就有签字人。因此 PIPL 的义务不是"现在就存在"，而是"接入真实客户数据的第一天就会触发"。

**核心义务 → 对本系统的映射**：

| 义务 | 落地要求 |
|---|---|
| 告知—同意 | 用户告知书与同意记录；员工信息须有合法性基础 |
| 最小必要 | **默认不展示**完整姓名，按角色脱敏（如"张*"或仅显示角色） |
| 存储期限 | 明确保留期与到期删除机制 |
| 境内存储 | 个人信息存于中国境内（→ 见 2.5） |
| 影响评估（PIA） | 处理敏感个人信息前需做个人信息保护影响评估 |
| 单独同意 | 处理**敏感**个人信息（如生物识别）需单独同意 |

**Demo 与生产的差异**：正因为演示数据不含个人信息，这套系统**目前完全没有**脱敏、保留期、访问控制或 PIA 机制。接入真实客户数据时需要从零建设——这不是"改个显示字段"，而是要补齐四项能力：角色化脱敏展示、存储期限与到期删除、处理活动记录、个人信息保护影响评估流程。

### 2.4 数据安全法（DSL）与数据分类分级

**依据**：《数据安全法》（2021-09-01 施行）+《数据安全技术 数据分类分级规则》(GB/T 43697-2024)

**要求**：数据处理者须建立**数据分类分级**制度，识别**重要数据**并编制重要数据目录。

**对本项目的判断难点**：

- 制造业图纸通常属于**商业秘密**，不必然是"重要数据"
- ⚠️ **但行业相关**：若涉及国防军工、关键基础设施、或特定行业的图纸，可能被认定为重要数据
- ⚠️ 多租户平台汇集数据后，整体敏感性上升

**技术侧要做的**：在数据模型上预留**分级标签**（如 `classification: public | internal | confidential | important`），并让访问控制、审计、出境策略都依赖这个标签。**这个字段现在不加，以后加会很痛。**

---

### 2.5 数据出境

**依据**：《数据出境安全评估办法》+《促进和规范数据跨境流动规定》（2024-03）

**三条合规路径**：安全评估／标准合同备案／保护认证。

**对本项目的核心场景**：**日本总部需要访问中国区数据吗？**

- **场景 A：总部只看聚合统计，不看原始图纸** → 风险最低，建议按此设计
- **场景 B：总部需查看客户原始图纸** → 可能触发数据出境路径 ⚠️

**设计建议**：

1. **优先做"数据不出境"的架构**——总部通过中国区系统的远程访问（而非数据复制出境）来查看，是中国区团队最应坚持的方案
2. 若必须出境，走标准合同或安全评估（阈值与豁免情形需按最新规定确认 ⚠️）
3. **技术前置**：数据模型上标记数据来源与可出境属性，避免事后逐张图纸人工判定

---

### 2.6 ICP 备案与许可证

**依据**：《互联网信息服务管理办法》

| 类型 | 适用 | 要求 |
|---|---|---|
| **非经营性 ICP 备案** | 不通过互联网有偿提供信息服务 | 备案 |
| **经营性 ICP 许可证** | 通过互联网有偿提供信息服务 | 增值电信业务经营许可证 ⚠️ |

**对本项目的判断**：面向企业客户**收费**提供 SaaS 服务，通常被认为属于经营性，可能需办理 **ICP 许可证**（信息服务业务类）。⚠️ 需与法务确认具体类别。

**与等保的关系**：**ICP 与等保是两套独立体系**，都要办，不能互相替代。

| 等保控制项 | 阿里云 | 腾讯云 |

| 边界防护 | 云防火墙 / WAF | 云防火墙 / WAF |
| 入侵检测 | 云安全中心 | 主机安全 |
| 集中日志（3 级安全管理中心） | 日志服务 SLS | 日志服务 CLS |
| 密钥管理（国密） | KMS（支持国密） | KMS（支持国密） |
| 数据库 | RDS（含 TDE） | TencentDB |
| 对象存储（图纸） | OSS + 服务端加密 | COS + 服务端加密 |
| 备份与容灾 | 混合云备份 HBR | 云备份 |

| 堡垒机／运维审计 | 堡垒机 | 云堡垒机 |

> **表达要点**：这套映射说明**合规要求可以直接翻译成云产品清单和预算**——这是项目经理能在立项会上给出的东西。

## 4. 与日本总部的协同边界

这是"跨文化运营落地"的具体化，也是中国区负责人最需要明确的边界。

| 事项 | 谁决定 | 说明 |
|---|---|---|
| 等保定级 | **中国区提出，总部确认** | 定级决定成本，必须双方签字 |
| 云厂商与地域选型 | **中国区** | 依赖中国区资质与客户要求 |
| 国密改造方案与排期 | **中国区主导** | 涉及密码库、KMS、数据迁移 |
| 数据分类分级标准 | **共同制定** | 需与总部产品数据模型对齐 |
| 是否符合日本侧出口管制 | **总部确认** | 日本《外汇法》对技术输出的要求 ⚠️ |
| 客户数据能否出境 | **中国区提出红线，总部配合** | 建议默认不出境 |
| 巡检与故障响应流程 | **共同制定** | 时差与值班安排需前置约定 |

> **底线原则**：涉及中国法律强制的合规事项（等保、密评、PIPL），**中国区不能因为总部排期而妥协**——这是中国区负责人必须守住的位置，也要在入职初期就讲清楚。

## 5. 落地路线图

| 阶段 | 时间 | 交付 |
|---|---|---|
| **阶段 0：合规前置调研** | 1–2 个月 | 等保定级结论、数据分类分级标准、出境路径结论、云厂商选型 |
| **阶段 1：基础安全建设** | 2–3 个月 | SSO + RBAC + 审计日志 + 安全响应头 + 限流修复 + 境内部署 |
| **阶段 2：等保合规改造** | 3–6 个月 | 边界防护、集中日志、备份容灾；备案与测评 |
| **阶段 3：密码合规（如需）** | 与阶段 2 并行 | 国密改造、KMS 建设、密评 |

> **为什么阶段 1 在阶段 2 之前**：SSO／RBAC／审计日志是等保"安全计算环境"的基础项，先做可以避免重复改造。

## 6. 与本 Demo 的边界声明

本文档描述的是**生产目标**。本仓库中的 Demo **有意识地保持为演示形态**，不包含任何合规实现：

- 无鉴权、无审计、无国密、无数据分级
- 部署在境外（Render），仅用于公开演示
- 全部业务数据为虚构演示数据，不含任何客户信息

**本 Demo 的价值在于证明业务链路与责任边界可行**，不在于证明合规就绪。两者是不同阶段的工作。
